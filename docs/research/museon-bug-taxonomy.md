# Museon Python bug 修复分类（N1）

## 结论摘要

本次从 Museon `main` 可达历史中抽取并复核了 30 个真实 Python 修复提交。样本集中，Ruff 只命中 1 个“捕获宽泛异常后继续成功路径”的缺陷（1/30，3.3%）；Pyright strict 没有命中被修复缺陷（0/30）。外部接口/序列化契约、状态分支、数据完整性/分页、运行环境边界是最高频的四组问题，共 21/30（70.0%），两种现有工具对这些缺陷的命中率均为 0%。

这不是对 Ruff 或 Pyright 通用能力的否定：它们在父快照中报告了大量风格、缺失依赖、未知类型和测试私有成员问题，但这些诊断没有指出相应提交所修复的行为错误，因此没有计作命中。N2 规则应优先验证“变体相关状态谓词”“无完整性证明却结束分页/标记完成”“动态边界值未经形状归一化”三类模式。

## 高频且现有工具抓不住的类别

1. **外部接口与序列化契约（6/30）**：端点版本、SQL 参数类型、动态 JSON 形状和响应模型之间的实际契约不在普通 Python 类型系统中。Ruff 与 Pyright 均为 0/6。
2. **状态与分支遗漏（5/30）**：同一个布尔谓词被用于多个业务 variant，但字段要求并不相同；代码本身通常类型正确。两工具均为 0/5。
3. **数据完整性与分页（5/30）**：问题依赖顺序、分页、每键公平性和“完整”声明之间的语义证明。两工具均为 0/5。
4. **运行环境与部署边界（5/30）**：本地可见的 PATH、模块、常量或延迟预算在远端/旧版本环境中不成立。两工具均为 0/5。
5. **并发幂等与共享状态（4/30）**：任务恢复、所有权登记、幂等键和全局预算分散在多个函数或状态容器中。两工具均为 0/4。

布局/资源上限也是稳定盲区（3/30），但多数阈值来自外部系统或真实字体度量，若没有项目合同很难做成高精度通用 lint。异常吞掉样本已被 Ruff `BLE001` 命中，因此不进入前三条新规则。

## 前 3 个候选规则

### 1. `VARIANT_REQUIRED_FIELD`：变体无关的必填字段门

- **触发模式**：函数返回“ready/eligible/valid”之类状态；它无条件检查某字段存在，但该对象同时有枚举/字面量 discriminator，且其他分支或构造路径证明至少一个 variant 不要求该字段。
- **precision 风险**：字段也许由未显式表达的全局不变量保证；命名启发式会误判普通校验函数。首版应只在 discriminator 与字段要求都可从同文件构造/分支中证明时报告。
- **分析能力**：AST + 函数内数据流；若构造证据在工厂函数中，需要跨函数摘要。

### 2. `UNPROVEN_COLLECTION_COMPLETENESS`：无顺序/配额证明的完整性声明

- **触发模式**：多 key 的有界查询或分页结果被分组后标记为 complete，或仅因任意一项越过时间边界就停止分页；代码中没有每 key 限额、公认排序或单调性检查。
- **precision 风险**：数据库视图或供应商 API 可能在外部合同中保证稳定排序/公平配额。应允许项目合同声明这些效果，否则只对可见的全局 `limit`、多 key 查询和 complete sink 的组合报告。
- **分析能力**：AST + 数据流 + 跨函数效果摘要（查询的排序/limit、分页 token、complete sink）。

### 3. `UNNORMALIZED_DYNAMIC_BOUNDARY`：动态边界值直接进入结构化 sink

- **触发模式**：来源为 `Any`、无类型 mapping、文本 SQL 或外部 JSON 的值，直接用于二次下标/属性链，或进入严格响应模型、JSON/时间类型 SQL 参数；路径上没有 `isinstance`、解码器或 schema validation。
- **precision 风险**：框架驱动可能已在不可见层完成解码，生成类型也可能比注解更强。首版应要求明确的动态 source 与结构化 sink，并允许标记可信适配器。
- **分析能力**：AST + source-to-sink 数据流；可信适配器与返回值形状需要跨函数摘要。

## 局限

- 样本按修复信号和时间倒序选择，不是随机抽样；它回答“近期修复中哪些模式值得先做规则”，不能直接外推长期发生率。
- commit 是分析单位；一个提交可能包含同一事故的多个子缺陷，本文强制归入一个主类，因此类别计数不会重复膨胀。
- Pyright 临时环境解析了父快照内的 Python 模块，但没有安装每个历史提交对应的全部第三方依赖。严格模式因此产生额外未知/缺失依赖诊断；命中判定人工排除了这些噪声，不会把它们算成工具能力。
- 静态工具不能看到供应商、数据库、部署镜像或真实字体的运行时合同。候选规则只有在项目合同或可见代码证据足够强时才应发出高精度诊断。
